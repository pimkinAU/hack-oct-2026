# Что делает каждая папка `scripts/`

Эти файлы написал организатор кейса, мы их не меняли — они отвечают за
окружение: поднять базу, скачать данные, залить данные в `raw`. Наша часть
начинается после них: она лежит в `model/` и читает то, что эти скрипты
положили в схему `raw`.

## Цепочка запуска целиком

```
bash scripts/setup.sh
   │
   ├── 1. проверяет Docker и docker compose
   ├── 2. проверяет файлы проекта, при нехватке вызывает download_data.sh
   ├── 3. проверяет Python и psycopg2 (при нехватке ставит)
   ├── 4. docker compose up -d postgres  →  при ПЕРВОМ старте тома сам
   │        выполняет scripts/init/*.sql (это делает образ postgres)
   ├── 5. python scripts/load_raw.py    →  схемы, таблицы raw, загрузка CSV
   └── 6. печатает, что получилось
```

То есть `setup.sh` — это обёртка, которая вызывает остальные скрипты по порядку
и после каждого шага проверяет результат. Если шаг не прошёл, он останавливает
установку и пишет, что делать дальше.

`bash scripts/setup.sh --reset` перед шагом 4 делает
`docker compose --profile tools down -v` — удаляет контейнер **и том с данными**,
поэтому база поднимается совсем пустая, и `init/*.sql` выполняются заново.

## `scripts/setup.sh` (156 строк)

Установка целиком. Шесть шагов, каждый с проверкой:

1. **Docker.** Сначала `command -v docker` — есть ли команда. Потом
   `docker info` — запущен ли демон (установить и запустить Desktop — разные
   вещи, поэтому проверок две). Дальше ищет команду compose: сначала
   современная `docker compose`, если её нет — старая `docker-compose`, и
   запоминает её в переменную `DC`. Все последующие команды идут через `$DC`,
   поэтому на машине с старой версией скрипт работает без правок.
2. **Файлы.** Проверяет `docker-compose.yml` и оба файла `scripts/init/`. Потом
   считает `data/*.csv`; если меньше восьми — зовёт `download_data.sh`.
3. **Python.** Ищет `python3`, иначе `python`. Проверяет `import psycopg2`;
   если пакета нет, ставит его сам (сначала обычно, при отказе — с флагом
   `--break-system-packages`, это нужно на свежих Ubuntu/Debian, где pip ругается
   на системный python).
4. **Контейнер.** Поднимает **только** сервис `postgres`. `pgadmin` вынесен в
   compose-профиль `tools` и по умолчанию не стартует: образ весит ~400 МБ, и
   первый запуск выглядел бы как зависание. После `up` скрипт крутит цикл
   `pg_isready` до 60 раз с паузой 2 секунды — ждёт, пока база реально начнёт
   отвечать, а не просто поднимется контейнер.
5. **Загрузка.** Вызывает `load_raw.py`. Порт он не берёт «из головы», а
   вытаскивает из `docker-compose.yml` строкой `awk`: если там прописан
   `5433:5432`, скрипт подключится к 5433. Это спасает, когда основной порт
   занят чужим Postgres.
6. **Итог.** Показывает, какие схемы появились и сколько строк в `raw.orders` и
   `raw.order_items`, и печатает строку подключения.

Полезная деталь: `set -uo pipefail` стоит в начале, но `set -e` нет. Это
сознательно — ошибки обрабатываются вручную через `die`, и сообщение печатается
человеческим языком, а не логом bash.

## `scripts/download_data.sh` (37 строк)

Скачивает восемь исходных CSV в `data/`. Источник — официальный репозиторий
Olist (`raw.githubusercontent.com/olist/work-at-olist-data/master/datasets`).

Что важно:

* скрипт идемпотентен: перед скачиванием проверяет `[ -s "$DIR/$f" ]` — файл
  существует и не пустой, тогда пропускает его и пишет «уже есть». Можно
  оборвать качание и запустить заново;
* `curl -fsSL --retry 3`: `-f` — не считать успехом ответ 404 (иначе в файл
  записалась бы страница ошибки), `-s`/`-S` — тихо, но ошибки показывать,
  `-L` — ходить за редиректами;
* путь считается от самого скрипта (`dirname "${BASH_SOURCE[0]}"`), поэтому
  запуск из любой папки кладёт файлы в `data/` проекта, а не в текущую;
* в конце `du -sh` — показывает объем (61 МБ).

Данные в git не кладутся: в `.gitignore` стоит `data/*.csv`. Клонируешь
репозиторий — и `setup.sh` сам всё докачает.

## `scripts/load_raw.py` (211 строк)

Единственный скрипт, который трогает содержимое базы. Делает две вещи: создаёт
`raw`-слой и наливает в него CSV.

**Таблица `MAPPING`** (строки 41–105) — сердце скрипта: список «файл →
таблица → список колонок». Порядок колонок в списке обязан совпадать с
заголовком CSV, потому что `COPY` прилепляет значения по порядку, а не по именам.

**Что происходит при загрузке одного файла** (функция `load_file`):

1. `check_header` читает первую строку файла и сравнивает её с ожидаемым
   списком колонок. Если отличается — останавливает установку и печатает
   обе строки рядом. Это защита от «скачал не тот файл» или «авторы поменяли
   датасет»: без проверки кривые колонки молча приехали бы перепутанными.
2. `TRUNCATE TABLE` — таблицу чистим перед загрузкой, поэтому перезапуск
   не удваивает данные.
3. Файл читается с кодировкой `utf-8-sig`. У одного из файлов в начале стоит
   BOM; без `sig` первая колонка приехала бы с невидимым символом в имени.
4. `COPY ... FROM STDIN WITH (FORMAT csv, HEADER true)` — один быстрый заход,
   а не 112 650 отдельных `INSERT`.
5. `UPDATE ... SET _source_file = <имя файла>` — служебная колонка, чтобы
   потом можно было проверить, откуда приехала строка.
6. `SELECT count(*)` — чтобы напечатать число строк по каждой таблице.

**Транзакция одна на весь прогон** (`conn.autocommit = False`, блок
`with conn, conn.cursor()`): если упал последний файл, откатится всё, и в базе
не останется половины датасета.

**Зачем схемы создаются питоном** (строки 186–195). Файлы `scripts/init/`
образ postgres выполняет только один раз — при инициализации **пустого** тома.
Если том уже был, или папка `init` не смонтировалась, схем в базе не окажется.
Поэтому скрипт сам делает `CREATE SCHEMA IF NOT EXISTS raw/core/mart` и сам
выполняет `02_raw_ddl.sql`. Отсюда же наш нюанс: `docker compose down` без `-v`
оставляет том, и тогда `init` не отрабатывает — лечится `setup.sh --reset`.

**Аргументы:** `--host`, `--port`, `--db`, `--user`, `--password` (по умолчанию
всё совпадает с `docker-compose.yml`), и `--skip-ddl` — перезалить данные, не
пересоздавая таблицы `raw`.

**Идемпотентность и безопасность для нашей модели:** скрипт трогает только
схему `raw`. Таблицы `core` и `mart` он не удаляет и не пересоздаёт, так что
после повторной загрузки сырых данных нашу модель нужно только пересобрать
(`bash model/build.sh`), а не писать заново.

## `scripts/init/01_init.sql` (13 строк)

Создаёт три схемы и настраивает поиск:

* `raw` — сырые данные «как пришли»;
* `core` — наша модель;
* `mart` — витрины и ответы;
* `ALTER DATABASE marketplace SET search_path TO core, public` — чтобы имена из
  `core` были видны без префикса схемы. Наши запросы всё равно пишут `core.`
  явно: так понятнее, к какой схеме объект, и не зависит от настроек клиента.

Выполняется автоматически при первом старте контейнера (об этом — выше, в
разделе про `load_raw.py`).

## `scripts/init/02_raw_ddl.sql` (123 строки)

Восемь таблиц `raw`, которые повторяют структуру CSV один в один.

Главное решение здесь: **все колонки — `text`**, включая даты и деньги. Это не
ленивость, а правило сырого слоя: данные кладутся так, как пришли. Если объявить
колонку `timestamp`, а в файле попадётся пустая строка или мусор, `COPY` уронит
загрузку всей таблицы. Поэтому типы и чистка — забота слоя `core`, и мы этим
занимаемся в `model/01_core.sql` (везде `nullif(btrim(x), '')::numeric` и
`::timestamp`).

Ещё две служебные колонки в каждой таблице:

* `_source_file` — из какого файла строка (заполняет `load_raw.py`);
* `_loaded_at` — когда загрузили, `default now()`.

Первые строки комментариев в файле — подсказка про опечатки в именах колонок
(`product_name_lenght`, `product_description_lenght`): они такие в исходнике, и
переименовывать их нельзя, иначе разойдётся сверка заголовка в `load_raw.py`.

Соответствие файлов и таблиц (числа строк — из нашей базы):

## `docker-compose.yml` (не в `scripts/`, но часть той же цепочки)

* сервис `postgres` — образ `postgres:16-alpine`, логин/пароль `hack`, база
  `marketplace`, порт `5432:5432`, том `pgdata`, монтирование `./scripts/init`
  в `/docker-entrypoint-initdb.d` (только первый старт) и `./data` в `/data`;
* `healthcheck` через `pg_isready` — нужен, чтобы `pgadmin` не стартовал раньше
  базы, и чтобы `setup.sh` мог дождаться готовности;
* `POSTGRES_INITDB_ARGS: "--encoding=UTF8 --locale=C"` — кодировка UTF-8
  обязательна (в данных португальский текст), `locale=C` ускоряет инициализацию;
* сервис `pgadmin` в профиле `tools`: `docker compose --profile tools up -d`,
  потом http://localhost:8080, логин `hack@local.dev` / `hack`.

## Частые поломки и что они значат

| что видно | причина | что делать |
|---|---|---|
| «Docker установлен, но не запущен» | демон не поднят | открыть Docker Desktop и дождаться зелёного значка |
| «в папке data всё ещё N файлов вместо 8» | нет доступа к githubusercontent | скачать файлы вручную по списку из `download_data.sh` |
| «база не ответила за две минуты» | порт 5432 занят другим Postgres | поменять проброс на `5433:5432` и запустить `setup.sh --reset` |
| схем `raw`/`core`/`mart` нет, хотя скрипт отработал | том базы был создан раньше, `init` не выполнился | `bash scripts/setup.sh --reset` |
| «Заголовок файла не совпадает с таблицей» | скачан не тот файл или датасет обновили | перескачать файл, скрипт сам покажет расхождение |
| `ModuleNotFoundError: psycopg2` | pip не поставил пакет | `pip install psycopg2-binary` |

## Как это связано с нашей моделью

`scripts/` заканчивают работу на схеме `raw` — дальше ничего не трогают.
Дальше идём мы:

```
raw (550 759 строк, все колонки text)
  ↓  model/01_core.sql      — типы, ключи, зерно, флаги is_revenue
core (факты и измерения)
  ↓  model/02_mart.sql      — представления для отчётов
mart (витрины)
  ↓  model/03_answers.sql   — пять ответов блока А в mart.answer_q1…q5
  ↓  model/04_checks.sql    — 10 проверок, что ничего не потерялось
```

Именно из-за такого разделения повторная загрузка сырых данных (`load_raw.py`)
безопасна: модель пересобирается одним прогоном `model/build.sh` и даёт те же
цифры, что и на чистой базе.
