# Кейс «Модель маркетплейса: от корзины до выкупа»

Окружение и раздаточный материал для команд. Вам предстоит спроектировать
модель данных маркетплейса, наполнить её из сырой выгрузки и ответить
SQL-запросами на вопросы аналитиков.

Данные — [Brazilian E-Commerce Public Dataset by Olist](https://github.com/olist/work-at-olist-data),
550 759 строк в восьми файлах, период с сентября 2016 по октябрь 2018.

## Быстрый старт

```bash
bash scripts/setup.sh
```

Скрипт проверяет Docker, поднимает PostgreSQL, скачивает данные, создаёт
схемы и загружает 550 759 строк в схему `raw`. На каждом шаге проверяет
результат и при сбое объясняет, что чинить. Занимает меньше минуты.

Начать с чистого листа: `bash scripts/setup.sh --reset`

Подключение: `postgresql://hack:hack@localhost:5432/marketplace`

## С чего начать

1. [docs/handout.md](docs/handout.md) — задание, описание данных и что сдавать.
2. [docs/tasks.md](docs/tasks.md) — вопросы, на которые должна отвечать
   ваша модель.

Вопросов в файле пять, но это не весь список: ещё пять появятся там же
в середине хакатона. Заранее их нет намеренно.

Свои скрипты складывайте рядом — например, в папку `model/`. Главное,
чтобы модель собиралась из `raw` одним запуском и на чистой базе.

Как устроен каждый скрипт из `scripts/` — что он проверяет, что делает на каждом
шаге и что означает его ошибка — расписано в [scripts/SCRIPTS.md](scripts/SCRIPTS.md).

## Схемы в базе

- `raw` — исходные данные как есть, все колонки `text`. Менять не нужно.
- `core` — ваша модель. Основное место работы.
- `mart` — витрины и сохранённые ответы, если понадобятся.

Все колонки в `raw` объявлены как `text` намеренно: в raw-слой данные
кладут в том виде, в каком они пришли. Объяви дату как `timestamp` —
и одно пустое значение уронит загрузку целиком. Приведение типов
и чистка это уже работа по переносу в свою модель.

## Требования к окружению

Docker Desktop или Docker Engine с плагином compose. Python 3.10+
с пакетом `psycopg2-binary` — `setup.sh` поставит его сам, если нет.
SQL-клиент по вкусу: DBeaver, psql внутри контейнера или веб-клиент
pgAdmin (`docker compose --profile tools up -d`, потом
http://localhost:8080).

Логин и пароль `hack` / `hack` простые намеренно, это локальная
учебная база.

## Если что-то не работает

**Схем raw, core и mart нет в базе.** Скрипты из `scripts/init`
выполняются только при создании пустой базы. Если база уже была создана
раньше, схемы не появятся сколько ни перезапускай контейнер. Лечится:
`bash scripts/setup.sh --reset`

**DBeaver не показывает схемы, хотя скрипт отработал.** Кэш дерева.
Правый клик по соединению → Disconnect, потом подключиться заново.

**Порт 5432 занят.** Поменяйте проброс в `docker-compose.yml`
на `"5433:5432"` и запустите `bash scripts/setup.sh --reset`.

**`docker compose up` будто завис.** Образ pgAdmin весит около 400 МБ.
Он вынесен в профиль `tools` и по умолчанию не запускается — поднимайте
базу через `setup.sh`.

**Загрузка падает на `ModuleNotFoundError: psycopg2`.** Поставьте вручную:
`pip install psycopg2-binary`

# Наше решение

## Как поднять

```bash
bash scripts/setup.sh        # поднял базу и загрузил raw
bash model/build.sh          # модель, витрины, ответы, проверки
```

Windows: `powershell -File model/build.ps1`.

Либо всё одним файлом, прямо в SQL-клиенте (DBeaver, pgAdmin, `psql`):

```bash
psql -U hack -d marketplace -f model/all_in_one.sql
```

Это `model/01_core.sql` + `02_mart.sql` + `03_answers.sql` + `04_checks.sql`,
склеенные скриптом `model/make_all_in_one.sh` (`.ps1`). Каждый шаг сначала
удаляет свои таблицы, поэтому прогонять можно сколько угодно раз — результат
один и тот же. Файл `01_core.sql` — это и есть тот запрос, который перекладывает
данные из `raw` в нашу модель: он сам создаёт схему `core`, если её нет.

## Модель данных

Одна fact-таблица на каждый уровень, зерно подписано над каждой таблицей в коде.

| таблица | зерно (одна строка =) | строк | ключ |
|---|---|---|---|
| `core.fact_order_item` | один товар одного продавца в одном заказе | 112 650 | `order_id + order_item_id` |
| `core.fact_order` | заказ целиком | 99 441 | `order_id` |
| `core.fact_payment` | один платёж заказа | 103 886 | `order_id + payment_sequential` |
| `core.fact_review` | отзыв заказа | 99 224 | `order_id + review_id` |
| `core.dim_customer` | покупатель | 99 441 | `customer_id` |
| `core.dim_seller` | продавец | 3 095 | `seller_id` |
| `core.dim_product` | позиция каталога | 32 951 | `product_id` |
| `core.dim_category` | категория | 74 | `category_name` |
| `core.dim_calendar` | день периода 2016-09-04 … 2018-10-22 | 774 | `date_day` |
| `core.dim_order_status` | статус заказа | 8 | `order_status` |

Каждая строка сырой выгрузки осталась в модели: число строк фактов совпадает
с числом строк в соответствующих файлах `raw` — это первая проверка в
`04_checks.sql`. В `fact_review` все 99 224 строк отзывов, хотя разных
`review_id` только 98 410: у 547 заказов на один `review_id` приходится
несколько записей, поэтому ключ у таблицы из двух полей.

Витрины в `mart`: `v_monthly_revenue`, `v_seller_revenue`, `v_category_revenue`,
`v_customer_base`, `v_delivery_month`, `v_payment_mix`. Ответы на пять вопросов
лежат отдельными таблицами `mart.answer_q1 … answer_q5` — их можно перепроверить
обычным `select`.

**Выручка во всей модели определяется одним местом:** в `dim_order_status`
стоит признак `is_revenue`, и он равняется единице только для статуса
`delivered`. Дальше по модели ходит колонка `is_revenue`, а не разбросанные
по запросам условия. Заказ попадает в выручку, если он доставлен; сумма —
это стоимость товаров, доставка отдельно в колонке `freight_total`.

Проверено контрольными числами задания: `13 221 498.11` — это сумма `price`
по доставленным заказам. Если добавить доставку, получается `15 424 463.65`,
если брать все статусы — больше. Средний чек `159.88` при этом считается
по заказу целиком, то есть товары **плюс** доставка: `139.97 × 1.14 строки`.

него не входят: там 16 и 4 заказа, и ни один не успел быть доставленным, то
есть выручка по ним всё равно нулевая. Это хвост выборки, а не потерянный
месяц, поэтому в ответ их лучше не тащить — иначе вместо 24 строк выйдет 26.

В модели они при этом есть: `mart.v_monthly_revenue` отдаёт все месяцы
календаря, а окно выбирает уже запрос ответа. Так решение про границу периода
остаётся видимым, а не зашитым в загрузку.

## Ответ 3. Средний чек заказа

Запрос: `mart.answer_q3`.

| показатель | значение |
|---|---|
| средний чек, рублей | **159.88** |
| среднее число строк в заказе | 1.14 |
| среднее число единиц в заказе | 1.14 |
| средний чек без доставки | 137.04 |
| доставленных заказов | 96 478 |

Средний чек = средняя величина `(price + freight_value)` **по заказу**, то есть
сначала сумма складывается внутри заказа, и только потом берётся среднее по
заказам. Так чек остаётся свойством заказа, как и сказано в задании.

Почему не 139.97: это среднее по **строке** заказа, а не по заказу —
`(price + freight_value)` усреднено по 110 197 позициям дошедших заказов.
Разница ровно в число строк: `139.97 × 1.14 ≈ 159.88`. Уровень позиции нужен
для отчётов по товарам и продавцам, для чека он не подходит.

Что не сошлось: второй неверный ответ из задания, 123.75, у нас не воспроизводится
ни одной разумной комбинацией — средняя цена позиции выходит 119.98 (только
доставленные заказы) или 120.65 (все позиции). 139.97 при этом совпадает
до копейки, поэтому определение выручки и уровень мы нашли правильно; похоже,
123.75 считался по немного другому набору строк.

## Ответ 4. Покупатели и повторные покупки

Запрос: `mart.answer_q4`, источник — `mart.v_customer_base`.

| показатель | значение |
|---|---|
| всего покупателей | **96 096** |
| вернулись с заказом | 2 997 |
| доля вернувшихся | **3.12%** |

Покупатель — это `customer_unique_id`, а не `customer_id`. В исходных данных
`customer_id` привязан к заказу: у него 99 441 разных значений, тогда как людей
96 096. Один `customer_unique_id` встречается под несколькими `customer_id`
(до 17 штук) — площадка перевыпускала идентификатор при повторном заказе.
Считать по `customer_id` значит посчитать заказы, а не людей: покупателей
стало бы 99 441, а доля вернувшихся — **0%**, потому что под каждым
`customer_id` ровно один заказ и «повтора» в такой разбивке не видит вообще.

Тех же 2 997 людей видно и по этому признаку: ровно у 2 997
`customer_unique_id` больше одного `customer_id`. Числа сошлись, потому что
новый идентификатор появляется только когда человек заказывает снова.

Как распределены покупки по людям:

| число заказов | людей |
|---|---|
| 1 | 93 099 |
| 2 | 2 745 |
| 3 | 203 |

| 6 | 6 |
| 7 | 3 |

Итого те же 96 096, из них 2 997 сделали больше одного заказа — это и есть

Важное про нескладываемость: сумма «числа заказов» по этим категориям даёт
97 276, хотя заказов было 96 478 — 780 заказов содержат товары из нескольких
категорий. Категории как раз складываются по выручке (13 221 498.11), но заказы
между ними не делятся, поэтому «заказов по категориям» лучше показывать как
«число позиций», иначе сводка выглядит как ошибка округления.

## Проверки целостности

`model/04_checks.sql` печатает 10 проверок с колонкой `ok`; на текущих данных
везде `t` (истина):

| проверка | что сравнивается |
|---|---|
| 1–3 | сколько строк в `raw`, столько и в модели (заказы 99 441, позиции 112 650, платежи 103 886) |
| 4–5 | у каждого заказа есть покупатель, у каждой позиции — категория |
| 6 | выручка модели равна выручке, посчитанной напрямую из `raw` |
| 7–8 | сумма по категориям и сумма по продавцам равны общему итогу |
| 9 | календарь покрывает все месяцы, в которых были покупки |
| 10 | ключи фактов уникальны, дублей нет |

Рядом тот же файл печатает блок «что теряется при обычном join»: 775 заказов без
позиций (603 `unavailable`, 164 `canceled`, 5 `created`, 2 `invoiced`,
1 `shipped`), 4 заказа без платежей, 768 заказов без отзыва, 547 заказов
с несколькими отзывами и 789 строк отзывов с повторяющимся `review_id`. Все они
остались в модели — с нулями там, где данных реально нет.
