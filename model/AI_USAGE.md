# Как мы использовали ИИ

Инструмент: Claude Code (модель Claude Opus 5.5), работал прямо в репозитории и
с базой через `docker compose exec ... psql`. Ниже — что именно он сделал, как
мы проверили результат и какие решения принимали сами.

## Что делал ИИ

**Ревью модели.** Прочитал `01_core.sql`–`04_checks.sql` и сверил их с
`docs/tasks.md` и `docs/handout.md`. Нашёл и описал проблемы:

| что было | что стало |
|---|---|
| календарь начинался 4 сентября 2016, а не 1-го, и обрывался на последней покупке | целые месяцы 2016-09 … 2018-10 (791 день) от дат покупки, вручения и создания отзыва |
| ни одного внешнего ключа | 12 внешних ключей между фактами и измерениями |
| категория товара вычислялась в трёх местах | только в `dim_product`, остальные берут оттуда |
| `fact_order` считал суммы заново из `raw` | собирается из `fact_order_item`, `fact_payment`, `fact_review` |
| город продавца в позициях брался из `raw` без очистки | берётся из `dim_seller` |
| отчёт по категориям строился от продаж и группировался по названию | строится от справочника, группировка по ключу |
| доля опозданий занижена: в знаменателе 8 заказов без даты вручения | знаменатель — заказы, где опоздание можно посчитать |
| проверки только печатали `ok`, сборка не падала | 13 проверок, при провале любой сборка падает с ошибкой; полноту ключей держат `not null` и внешние ключи |
| месяц заказа разбирался из `raw` в трёх фактах | один раз во временной `stg_order`, все факты берут оттуда |
| проверки 11–12 сравнивали модель саму с собой, проверка 14 не могла упасть | суммы сверяются с выручкой из `raw`, категории — с карточками товаров |

**Второй круг — автоматическое ревью** (`/code-review` в Claude Code) по нашим же
правкам нашло 8 мест: выдуманный нулевой месяц 2018-11 в витрине по месяцам, проверки,
которые не могли упасть, разное поведение `is_revenue` при отсутствии статуса, отзывы
вне границ календаря. Все исправлены и перепроверены пересборкой.

**Третий круг — чистка кода** (`/simplify`, четыре параллельных проверки: повторное
использование, упрощение, эффективность, глубина исправления). Убраны неиспользуемые
копии города продавца и названия категории из `fact_order_item`, календарь стал
строиться последним из готовых фактов и потерял выдуманный месяц 2018-11 в корне,
а не фильтром в витрине; поля из `raw` разбираются по одному разу; две проверки
заменены ограничениями схемы. Цифры и проверки после пересборки не изменились.

**Разбор на данных.** Посчитал то, что нужно уметь объяснить на защите:
8 заказов `delivered` без даты вручения (1 249.18 выручки), 6 недоставленных
с датой вручения; три определения «вернувшегося покупателя» (2 997 / 2 801 / 848
с заказами в один день); отсутствие дублей пары `(order_id, review_id)`.

**Документация.** Обновил `README.md`, `NOTES.md`, `ANSWERS.md` под новые цифры,
написал `CLAUDE.md` в корне — инструкцию для ИИ по этому репозиторию.

## Как проверяли результат

1. **Контрольные цифры задания** после каждой пересборки: 24 строки и
   13 221 498.11; 226 987.93; 159.88 / 1.14 / 1.14; 96 096 и 3.12%; 74 категории
   и 1 233 131.72. Все сошлись.
2. **Построчное сравнение старой и новой модели.** Перед пересборкой сохранили
   копию `fact_order`, `fact_order_item`, `dim_category` и сравнили построчно:
   0 отличающихся строк. Правки поменяли устройство кода, а не цифры.
3. **Сборка с нуля:** `bash scripts/setup.sh`, потом `bash model/build.sh` —
   внешние ключи встали, значит в данных нет «сирот».
4. **Проверка самих проверок.** Подменили одну проверку на заведомо ложную —
   сборка упала с ошибкой и кодом 3, как и должна.
5. **Что ИИ не смог подтвердить, так и записали:** цифру 123.75 из задания
   («средняя цена товара без доставки») воспроизвести не удалось ни одним
   вариантом расчёта (120.65, 119.98, 136.68), на наш ответ она не влияет.
