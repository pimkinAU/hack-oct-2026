# Задание 9. Способы оплаты и рассрочка

## Что спрашивают

Из `docs/tasks.md`:

> По штатам покупателя за 2018 год, плюс разрез по способам оплаты целиком.
> **Результат:** штат, число платежей, сумма, средний срок рассрочки.
> Отдельно: способ оплаты, число платежей, средний срок рассрочки.

## В чём ловушка

* **Уровень.** Платёж — не заказ: заказ, оплаченный картой и ваучером, даёт два
  платежа. «Число платежей» — это строки `fact_payment`, а не заказы.
* **Какой штат.** Как в вопросе 7 — штат на момент заказа (`fact_order`), а не
  текущий адрес человека.
* **Какие платежи.** Только по заказам с `is_revenue`, как вся выручка модели:
  деньги отменённых заказов вернулись покупателю. Из-за этого в разрезе по
  способам нет `not_defined` — эти 3 платежа все на отменённых заказах.
* **Сумма — с доставкой.** `payment_value` — то, что заплатил покупатель, то
  есть товары + доставка. Это не выручка в смысле модели.

## Откуда берутся цифры

```
core.fact_payment        одна строка = один способ оплаты заказа,
   ↓                     installments, payment_value, month_start
core.fact_order          customer_state на момент заказа
   ↓
mart.answer_q9           2018 год, по штатам
mart.answer_q9_type      весь период, по способам оплаты
```

## Запрос дословно

```sql
create table mart.answer_q9 as
select fo.customer_state,
       count(*)                             as payments,
       round(sum(p.payment_value), 2)       as paid,
       round(avg(p.installments), 2)        as avg_installments
from core.fact_payment p
join core.fact_order fo on fo.order_id = p.order_id
where p.is_revenue
  and p.month_start between date '2018-01-01' and date '2018-12-01'
group by fo.customer_state
order by paid desc, fo.customer_state;

create table mart.answer_q9_type as
select p.payment_type,
       count(*)                             as payments,
       round(avg(p.installments), 2)        as avg_installments
from core.fact_payment p
where p.is_revenue
group by p.payment_type
order by payments desc, p.payment_type;
```

Разбор по строчкам:

* `from core.fact_payment p join core.fact_order fo` — основа — платежи, к ним
  приклеиваем штат заказа. Тут обычный `join` безопасен: платежей без заказа
  нет (0 строк при `left join ... where fo.order_id is null`), строки не теряются
  и не множатся — на один платёж один заказ;
* `count(*)` — платежи, а не `count(distinct order_id)`;
* `p.month_start between '2018-01-01' and '2018-12-01'` — 2018 год по месяцу
  покупки (`month_start` платежа взят из заказа). Отдельной даты оплаты в
  данных нет;
* `sum(p.payment_value)` — сколько заплатили, с доставкой;
* `avg(p.installments)` — средний срок по платежам. У карты бывает и 10, и 1,
  у остальных способов всегда 1;
* второй запрос — без штата и без года: «по способам оплаты целиком».

## Почему нельзя было иначе

* **заказы вместо платежей** — за 2018 год 52 783 заказа против 54 748 платежей:
  разница — заказы, оплаченные несколькими платежами (чаще всего карта + ваучер,
  1 049 заказов; ещё 210 — несколько ваучеров);
* **все статусы** — 56 015 платежей на 8 699 763.05 и пятый способ `not_defined`.
  Деньги отменённых заказов не остались у магазина;
* **выручка вместо платежей** (`goods_total`) — 7 218 125.12: без доставки, а
  вопрос про то, что заплатил покупатель;
* **штат по текущему адресу** — как в вопросе 7: платёж за заказ, оформленный
  до переезда, ушёл бы в новый штат.

## Что ещё видно из этих чисел

* рассрочка бывает только у кредитной карты, у остальных способов срок всегда 1;
  поэтому средний срок по штату — это во многом доля карт и размер чека;
* самая длинная рассрочка — на северо-востоке (PB 3.67, RN 3.63, SE 3.56),
  самая короткая — в SP (2.51).
