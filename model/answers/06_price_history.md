# Задание 6. Как менялась цена одного товара

## Что спрашивают

Из `docs/tasks.md`:

> Возьмите товар, который продавался по наибольшему числу разных цен,
> и покажите историю его цены.
> **Результат:** дата, цена, продано единиц.

## В чём ловушка

* **Что значит «продавался».** Берём, как и выручку во всей модели, только
  позиции доставленных заказов (`is_revenue`). На этих данных лидер тот же и по
  всем статусам — 31 цена, — но правило одно на всю модель.
* **Ничья.** Если у двух товаров одинаковое число цен, без второго ключа
  сортировки ответ может меняться от запуска к запуску. Второй ключ — `product_id`.
* **Одна дата — несколько цен.** В один день товар уходил и по двум ценам
  (например, 2018-03-19: 47.65 и 59.89). Склеивать их нельзя, поэтому строка
  ответа — пара «день + цена», а не день.

## Откуда берутся цифры

```
core.fact_order_item     одна строка = единица товара в заказе,
   ↓                     есть purchased_at, price, is_revenue
подзапрос p              товар с наибольшим count(distinct price)
   ↓
mart.answer_q6           день покупки, цена, сколько единиц
```

## Запрос дословно

```sql
create table mart.answer_q6 as
select i.purchased_at::date as sale_date,
       i.price,
       count(*)             as units_sold
from core.fact_order_item i
join (
    select product_id
    from core.fact_order_item
    where is_revenue
    group by product_id
    order by count(distinct price) desc, product_id
    limit 1
) p on p.product_id = i.product_id
where i.is_revenue
group by i.purchased_at::date, i.price
order by sale_date, price;
```

Разбор по строчкам:

* подзапрос `p` — выбор товара. `count(distinct price)` считает разные цены,
  а не продажи: товар, проданный 500 раз по одной цене, сюда не попадёт.
  `order by ..., product_id` разбивает ничью, `limit 1` оставляет одного;
* `where is_revenue` стоит **дважды**: и при выборе товара, и в истории. Если
  убрать его во внешнем запросе, в историю попадут позиции отменённых заказов —
  цена, по которой товар так и не продали;
* `i.purchased_at::date` — дата покупки без времени. Цена в позиции — та, что
  была в момент оформления заказа, поэтому и дата нужна оформления, а не доставки;
* `group by i.purchased_at::date, i.price` — строка ответа = день + цена;
* `count(*)` — проданные единицы: в `fact_order_item` одна строка — это одна
  единица товара (так устроен `raw.order_items`, поля «количество» там нет).

## Что получилось

Товар `437c05a395e9e47f9762e677a7068ce7` (health_beauty): **31 разная цена**,
от 44.98 до 59.90, продано 151 единица с 19 февраля по 17 августа 2018 —
76 строк «день + цена». Следующие по числу цен — 29 и 27.

## Почему нельзя было иначе

* **строка = день** — 70 строк вместо 76: в пять дней товар уходил по
  нескольким ценам (в четыре — по двум, в один — по трём), и их пришлось бы либо усреднять (такой цены не было ни у одной
  продажи), либо выбрасывать одну из них;
* **все статусы** — товар тот же и цен столько же (31), но единиц 155, а не 151:
  четыре единицы из отменённых и не доехавших заказов. Ответ «продано» с ними
  был бы неправдой;
* **без второго ключа сортировки** — сейчас лидер один (31 против 29), но
  запрос не должен зависеть от того, что так совпало на этих данных;
* **товар с самой большой разницей цен** (`max - min`) — это другой вопрос:
  одна скидка дала бы большой разброс при двух ценах.

## Что ещё видно из этих чисел

* в конце февраля цена росла почти каждый день (44.98 → 52.30 за неделю) —
  похоже на подбор цены после запуска товара;
* пик продаж — 20–22 марта по 47.65 (28 единиц за три дня): самая низкая цена
  после февральского роста;
* дальше цена держится в коридоре 48–54 и меняется раз в одну-две недели.

## Как перепроверить

```sql
select count(distinct price), sum(units_sold) from mart.answer_q6;
```

Ожидаем `31` и `151`.
