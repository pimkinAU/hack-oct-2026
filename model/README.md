# Модель данных Capibara

Папка `model/` — решение кейса «Модель маркетплейса: от корзины до выкупа».
Сырьё лежит в `raw` (его не трогаем), модель собирается в `core`, витрины и
готовые ответы — в `mart`.

## Как собрать

Сначала данные (если ещё не подняты):

```bash
bash scripts/setup.sh
```

Что этот скрипт делает шаг за шагом и как читать его ошибки — расписано в
[../scripts/SCRIPTS.md](../scripts/SCRIPTS.md).

потом модель:

```bash
bash model/build.sh                    # Linux / macOS / WSL
```

```powershell
powershell -File model/build.ps1       # Windows
```

Можно и одним файлом, прямо в SQL-клиенте (DBeaver, pgAdmin, `psql`) — там нет
никаких метакоманд psql, только обычный SQL:

```bash
psql -h localhost -U hack -d marketplace -f model/all_in_one.sql
# или внутри контейнера:
docker compose exec -T postgres psql -U hack -d marketplace < model/all_in_one.sql
```

Проверено: файл поднимает модель даже на базе, где схем `core` и `mart` вообще
нет (их создаёт сам `01_core.sql`).

Модель всегда строится с нуля: `01_core.sql` сначала удаляет свои таблицы и
создаёт их заново, поэтому запуск можно повторять сколько угодно раз, и результат
на чистой базе и на перезапущенной одинаковый. Проверено на базе, снятой вместе
с томом (`docker compose down -v`), — все ответы и проверки совпали.

## Файлы

| файл | что делает |
|---|---|
| `01_core.sql` | строит `core`: факты и измерения из `raw`, историю категорий и адресов (SCD2) из `raw` + журнала `changelog`; сам создаёт схемы, если их нет |
| `02_mart.sql` | представления `mart`: выручка по месяцам, продавцам, категориям, доставка (по месяцам и штатам), воронка статусов, оплата, покупатели |
| `03_answers.sql` | десять вопросов из `docs/tasks.md` (блоки А и Б), ответы кладёт в `mart.answer_q1…q10` и печатает контроль |
| `answers/` | по одному файлу на задание из `03_answers.sql`: условие, ловушка, запрос дословно, результат, как перепроверить |
| `04_checks.sql` | 15 проверок целостности: строки, ключи, суммы, потери на join, история; в конце проба вброса с откатом |
| `all_in_one.sql` | те же четыре шага одним файлом: можно запустить в DBeaver, pgAdmin или `psql -f` |
| `make_all_in_one.sh` / `.ps1` | собирают `all_in_one.sql` из четырёх шагов; правки всегда вносятся в шаги, а файл перегенерируется |
| `build.sh` / `build.ps1` | прогоняют четыре шага подряд и печатают, на каком шаге упало |
| `explore*.sql` | разведка данных: чем отличаются ключи, где пропуски, какие бывают статусы |
| `verify.sql` | поиск определения выручки: перебор вариантов «что считать» и сверка с контролем |
| `ANSWERS.md` | ответы с цифрами и разбором контрольных точек |
| `TASKS_DEFENSE.md` | тот же разбор крупнее, для защиты: что спрашивают, ловушки, как отвечать на уточняющие вопросы |
| `NOTES.md` | записка о решениях: что выбрали, от чего отказались, почему |
| `DASHBOARD.md` | концепция дашборда «доставка и обещания» |
| `STRATEGY.md` | куда растёт модель и где потолок PostgreSQL |

## Что где лежит в базе

**`core` — модель.**

| таблица | зерно (одна строка это…) | строк |
|---|---|---:|
| `fact_order` | заказ целиком | 99 441 |
| `fact_order_item` | один товар одного продавца в заказе | 112 650 |
| `fact_payment` | один способ оплаты заказа | 103 886 |
| `fact_review` | один отзыв (ключ `order_id + review_id`) | 99 224 |
| `dim_customer` | запись покупателя о заказе | 99 441 |
| `dim_customer_address` | версия адреса человека (SCD2) | 96 355 |
| `dim_seller` | продавец | 3 095 |
| `dim_product` | карточка товара, категория текущая | 32 951 |
| `dim_product_category_hist` | версия категории товара (SCD2) | 32 951 + изменения |
| `dim_category` | категория, включая `not_available` | 74 |
| `dim_order_status` | статус заказа и признак «считать выручкой» | 8 |
| `dim_calendar` | день календаря | 774 |

**`mart` — витрины.** `v_monthly_revenue`, `v_seller_revenue`, `v_category_revenue`,
`v_customer_base`, `v_delivery_month`, `v_delivery_state`, `v_order_status`,
`v_payment_mix`, плюс `answer_q1…q10` (и `answer_q9_type`).

**`changelog` — журнал изменений.** `product_category_change`, `customer_move`.
Пересборка эту схему не удаляет. Писать в неё через функции
`changelog.change_product_category(...)` и `changelog.move_customer(...)` —
подробно в [answers/11_history.md](answers/11_history.md).

## Одно соглашение на весь проект

**Выручка = сумма `price` по заказам со статусом `delivered`, без стоимости доставки.**
Признак `is_revenue` лежит в `fact_order` и `fact_order_item`, поэтому в отчётах не
нужно помнить список статусов. Обоснование — в `NOTES.md`.
