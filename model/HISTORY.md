# История изменений: категория товара и адрес покупателя

Это ответ на два требования из условия («вброс»), которые нельзя выполнить в
модели-снимке. Файл модели: `model/05_history.sql`, проверки:
`model/07_checks_b.sql` (проверки 1–6).

## Что требуют

1. Продавец может поменять категорию товара, но отчёты за прошлые периоды должны
   оставаться прежними. Значит, модель обязана хранить историю категорий, а не
   только текущую.
2. Покупатели переезжают, и по любому заказу надо видеть адрес **на момент
   заказа**, а не текущий адрес человека.

## Почему в плоской модели это ломается

В выгрузке `raw.products` у товара одна строка с одной категорией — это состояние
«на сегодня». Таблицы `raw.order_items` и `raw.orders` тоже пришли снимком. Если
считать выручку по категории через `dim_product`, то вчерашняя продажа сегодня
посчитается по новой категории: продавец поменял категорию — и отчёт за февраль
переклеился. То же с адресом: `dim_customer` хранит адрес человека, и любой
переезд переписывает прошлые заказы.

Мы это наблюдали на своих же цифрах: выручка 13 221 498.11 по категориям держится
только пока никто ничего не меняет. Как только появляется изменение, у наивной
модели меняются прошлые периоды — а этого допускать нельзя.

## Как сделали: по одной строке на каждое состояние (SCD2)

Для каждого объекта, у которого может быть несколько состояний, заводим таблицу с
двумя датами — `valid_from` и `valid_to`. Строка таблицы описывает не «товар», а
«товар в таком-то виде с такой-то даты». Тогда заказ соединяется с той версией,
которая действовала в его дату, и прошлые отчёты не меняются никогда.

Три таблицы:

| таблица | ключ версии | что хранит | строк |
|---------|-------------|------------|-------|
| `core.dim_customer_history` | `customer_unique_id + valid_from` | адрес человека по датам | 96 338 |
| `core.dim_product_category_history` | `product_id + valid_from` | категорию товара по датам | 32 951 |
| `core.dim_seller_history` | `seller_id + valid_from` | адрес продавца по датам | 3 095 |

Плюс два представления, которые и делают «момент заказа» рабочим:

- `core.v_order_customer_address` — заказ + адрес покупателя на дату заказа;
- `core.v_item_category_as_ordered` — позиция + категория товара на дату заказа.

Границы промежутка. Версия действует с `valid_from` до `valid_to` включительно, а
`valid_to` — это день **перед** началом следующей версии. Если переезд случился
5 марта, старая версия заканчивается 4 марта, и заказ от 5 марта читается уже по
новой версии. Так ни один день не попадает в две версии сразу.

Действующая версия помечена `is_current = true`, у неё `valid_to = 9999-12-31`
(дальняя дата вместо `null`, чтобы соединение через `between` работало без
костылей с `coalesce` в каждом запросе).

## Откуда берутся даты, если журнала нет

Настоящего журнала изменений в выгрузке нет, и мы это не прячем:

- **Покупатели.** У человека (`customer_unique_id`) может быть несколько записей
  `customer_id` с разными адресами — так в обезличенной выгрузке выглядят переезды.
  В данных 252 человека имеют два и более разных адреса (город + штат + индекс),
  всего 96 352 пары «человек + адрес». Датой начала версии мы считаем дату самого
  раннего заказа с этого адреса. Это не дата переезда, а дата, когда адрес
  впервые появился в данных, — лучше, чем ничего, и для «адреса на момент заказа»
  этого достаточно.
- **Продавцы и категории.** У продавца и у товара в выгрузке по одному адресу и
  по одной категории, поэтому у них ровно одна версия (`valid_from` — дата первой
  продажи). История не пуста, а пуста история изменений: механизм готов принять
  её, как только придут данные changes.

Как это будет выглядеть, когда придут настоящие изменения категории — одна схема
на все три таблицы:

```sql
-- пришло изменение категории товара 42 на 'toys' с 1 января 2019:
update core.dim_product_category_history
   set valid_to = date '2018-12-31', is_current = false
 where product_id = '42' and is_current;

insert into core.dim_product_category_history
values ('42', 'toys', 'brinquedos', date '2019-01-01', date '9999-12-31', true);
```

После этого февральский отчёт останется таким, каким был, потому что февральские
позиции соединяются с версией, у которой `valid_to = 2018-12-31`.

## Как пользоваться

Адрес покупателя на момент заказа:

```sql
select fo.order_id,
       fo.purchased_at::date as ordered_on,
       h.customer_city,
       h.customer_state,
       h.zip_code_prefix
from core.fact_order fo
join core.dim_customer_history h
  on fo.customer_unique_id = h.customer_unique_id
 and fo.purchased_at::date between h.valid_from and h.valid_to;
```

Категория товара на момент заказа (и выручка по ней):

```sql
select h.display_category,
       round(sum(i.price)::numeric, 2) as revenue
from core.fact_order_item i
join core.fact_order fo on fo.order_id = i.order_id
join core.dim_product_category_history h
  on h.product_id = i.product_id
 and fo.purchased_at::date between h.valid_from and h.valid_to
where i.is_revenue
group by h.display_category
order by revenue desc;
```

Вторая проверка снизу важна не меньше самой выручки: сумма по этой истории равна
13 221 498.11, то есть ровно той выручке, что получена в блоке А другим путём.
История ничего не добавила и не потеряла.

## Что показал пример переезда

Демонстрация в конце `model/05_history.sql` сравнивает адрес на момент заказа с
текущим адресом человека. Вот первые строки (было на момент заказа → стало сейчас):

| заказ от | было | стало |
|----------|------|-------|
| 2017-09-06 | SP, sao caetano do sul | RS, canoas |
| 2018-01-08 | SP, sao paulo | SP, sao jose do rio preto |
| 2018-04-27 | SP, taboao da serra | SP, sao paulo |
| 2017-10-06 | SP, jaguariuna | SP, campinas |
| 2018-07-29 | PE, recife | MG, belo horizonte |
| 2017-06-15 | RJ, petropolis | SP, mogi das cruzes |
| 2018-04-14 | SP, sao paulo | SC, criciuma |
| 2018-06-04 | MG, uberaba | SE, aracaju |

У 238 человек больше одной версии адреса. Если бы мы считали географию выручки по
текущему адресу, эти люди попали бы не в тот штат: например, заказы из Recife
2017 года сегодня висели бы на Minas Gerais.

## Как это проверяется

`model/07_checks_b.sql`, проверки 1–6 (колонка `ok`, везде должно быть `t`):

1. у каждого человека ровно одна действующая версия (96 096 = 96 096);
2. версии одного человека не пересекаются (0 пересечений);
3. каждый из 99 441 заказов получает ровно одну версию адреса;
4. каждая из 112 650 позиций получает ровно одну категорию на дату заказа;
5. выручка, посчитанная через историю категорий, равна 13 221 498.11;
6. у продавца одна версия (3 095 = 3 095), то есть история не наплодила теней.

Проверка 2 и проверка 3 поймали настоящую ошибку. Сначала `valid_to` мы ставили
равным дате начала следующей версии, и пограничный день оказывался сразу в двух
версиях: проверка 2 нашла 242 пересечения, а проверка 3 насчитала 99 685 строк на
99 441 заказа — у заказов на пограничную дату находилось два адреса сразу.
Исправили на «день перед следующей версией» — стало 0 и 99 441.

## Что было неочевидно в реализации

- Подзапрос «когда начался следующий адрес», посчитанный на каждую из 96 тысяч
  строк по представлению, висел больше двадцати минут. Помогло то, что
  промежуточный список адресов стал отдельной таблицей с индексом, а даты конца
  версии считаются одним соединением таблицы с самой собой и группировкой
  (`update … from (select … group by …)`). Секунды вместо минут.
- Из двух адресов, появившихся у человека в один день, остаётся тот, с которого
  заказов больше (при равенстве — первый по алфавиту). Таких столкновений 14 из
  96 352: человек физически не может жить в двух городах, это шум выгрузки.
  Число столкновений печатается прямо в `model/05_history.sql`, чтобы приём не
  был невидимым.
- В контейнере Docker `/dev/shm` 64 МБ, и параллельный план большой проверки
  падает с «No space left on device». В `model/07_checks_b.sql` поэтому стоит
  `set max_parallel_workers_per_gather = 0`.
